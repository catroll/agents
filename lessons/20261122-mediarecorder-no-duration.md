# Browser recordings have no container duration — probe after transcoding

**Signal.** A file the browser just recorded fails with "读不出音频时长"
(`ffprobe` parsed nothing), while a file generated by ffmpeg in the same format
works. `ffprobe -show_entries format=duration` on the browser file prints `N/A`,
and so does `-show_entries stream=duration`.

**Cause.** `MediaRecorder` writes a non-seekable WebM/OGG stream: there is no
Duration element, because the muxer never goes back to patch the header.
`ffprobe` legitimately reports `N/A`. The audio decodes fine — only the metadata
is missing.

**Check.**

```bash
ffprobe -v error -show_entries format=duration -of default=nw=1:nk=1 rec.webm
# N/A
ffmpeg -v error -i rec.webm -f null -          # decodes; no error
ffmpeg -y -i rec.webm -ar 16000 -ac 1 -c:a pcm_s16le rec.wav
ffprobe -v error -show_entries format=duration -of default=nw=1:nk=1 rec.wav
# 2.000000
```

**Fix.** Compute the duration after transcoding to PCM WAV (which always carries
it), or count decoded samples / packets. Do not reject a browser upload because
the container lacks a duration, and do not trust `format=duration` as the only
source: fall back to `stream=duration`, then to a decoded-length estimate.

**Evidence (2026-11-22).** `ffmpeg ... -f webm - | cat > live.webm` reproduces
the MediaRecorder shape: `format=duration` → `N/A`, `stream=duration` → `N/A`,
but the transcoded WAV → `2.000000`. The proxy rejected it with
`400 读不出音频时长`; after probing the WAV it returned `200 duration=2.0`.
A real Firefox `MediaRecorder` recording (`audio/ogg;codecs=opus`, 41 KB,
2.4 s) then assessed end-to-end.
